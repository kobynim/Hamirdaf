# המרדף הארגוני — גרסה רב-משתתפים + חבילות תוכן

משחק למידה בהשראת "המרדף": כל משתתף משחק מהמסך שלו (טלפון/מחשב), בלי מסך מנחה משותף. המצב המשותף (תור מי, קופה, מי שרד, מיקום במרדף) מתעדכן בזמן אמת דרך Firebase Realtime Database. בנק השאלות טעון מתוך "חבילות תוכן" (content packs) נפרדות, כך שאפשר להריץ גרסאות שונות (נושאים/קושי שונה) בלי לגעת בקוד.

## מה יש בחבילה

```
index.html                 <- המשחק עצמו: לובי/יצירת חדר/הצטרפות/משחק.
content-editor.html        <- עורך תוכן גרפי לחבילות שאלות (JSON), בלי לגעת בקוד.
firebase-config.js         <- קונפיגורציית פרויקט Firebase שלכם (יש למלא לפני שימוש).
database.rules.json        <- הצעת חוקי אבטחה בסיסיים ל-Realtime Database.
content-packs/
  manifest.json             <- רשימת חבילות התוכן הזמינות (מוצגת בבחירה ביצירת חדר).
  core-v1.json               <- חבילת התוכן המקורית (40 שאלות: תהליכי ליבה + טופס 17).
  onboarding-v1.json         <- חבילת דוגמה קטנה (קליטת עובדים חדשים) — דוגמה להוספת חבילה.
assets/
  chaser-amnon-asher.jpg     <- תמונת ה"רודף" (אמנון אשר).
questions.js                <- קובץ הליבה הישן (לפני המעבר לחבילות) — נשמר כרפרנס בלבד,
                                המשחק כבר לא טוען אותו ישירות (הוחלף ב-content-packs/core-v1.json).
```

## שלב 1: הקמת פרויקט Firebase

1. גשו ל-[Firebase Console](https://console.firebase.google.com/) וצרו פרויקט חדש (או השתמשו בפרויקט קיים).
2. בתפריט הצד: **Build → Realtime Database → Create Database**. בחרו מיקום, והתחילו במצב "locked mode" (נשנה את החוקים בעצמנו מיד).
3. גשו ל-**Project settings → General → Your apps**, לחצו על סמל ה-Web (`</>`) כדי לרשום אפליקציית ווב חדשה (לא צריך Hosting של Firebase עצמו — סטטי בלבד).
4. Firebase יציג אובייקט קונפיגורציה בסגנון:
   ```js
   const firebaseConfig = {
     apiKey: "...",
     authDomain: "...",
     databaseURL: "...",
     projectId: "...",
     storageBucket: "...",
     messagingSenderId: "...",
     appId: "..."
   };
   ```
   העתיקו את הערכים לתוך `firebase-config.js` (במקום הפלייסהולדרים `YOUR_...`).

   **הערה על אבטחה:** `apiKey` כאן הוא מזהה ציבורי של הפרויקט, לא סוד שרת — זה תקין שהוא גלוי בקוד הצד-לקוח. האבטחה האמיתית של הנתונים נשענת על ה-**Security Rules** של Realtime Database (השלב הבא), לא על הסתרת הקובץ הזה.

## שלב 2: חוקי אבטחה (Security Rules)

בקובץ `database.rules.json` המצורף מוגדרים חוקים בסיסיים:

```json
{
  "rules": {
    "rooms": {
      "$roomCode": {
        ".read": true,
        ".write": true
      }
    },
    ".read": false,
    ".write": false
  }
}
```

זה מאפשר קריאה/כתיבה חופשית (בלי אימות משתמשים) רק תחת `rooms/{roomCode}` — כלומר רק למי שמכיר קוד חדר ספציפי — וחוסם הכל מחוץ לזה. זו **רמת אבטחה בסיסית** המתאימה למשחק פנים-ארגוני שאינו חשוף לאינטרנט הפתוח (כל מי שמנחש/מקבל קוד חדר יכול לקרוא ולכתוב לחדר הזה).

כדי להחיל את החוקים:
- ב-Firebase Console: **Realtime Database → Rules**, הדביקו את תוכן `database.rules.json` ולחצו **Publish**.
- או דרך ה-CLI: `firebase deploy --only database` (דורש התקנת `firebase-tools` והרצת `firebase init` מקומית מול הפרויקט).

**אם המשחק ייחשף מחוץ לרשת הארגון** (למשל דרך קישור פומבי לא-מוגן), מומלץ להוסיף לפחות Firebase Auth אנונימי (`signInAnonymously`) ולהגביל כתיבה למשתמשים מאומתים, כדי למנוע ואנדליזם על חדרים פעילים. זה לא ממומש בגרסה הנוכחית (MVP).

## שלב 3: הרצה מקומית

הקבצים טוענים תוכן דרך `fetch()` (למשל `content-packs/manifest.json`), ורוב הדפדפנים **חוסמים `fetch` לקבצים מקומיים כשפותחים קובץ HTML ישירות (`file://`)**. לכן יש להריץ שרת סטטי מקומי פשוט מתיקיית הפרויקט:

```bash
# אפשרות 1: Python (מובנה ברוב המערכות)
python3 -m http.server 8080

# אפשרות 2: Node (ללא התקנה, דרך npx)
npx serve . -l 8080
```

לאחר מכן גשו ל-`http://localhost:8080` בדפדפן. לבדיקה מרובת-משתתפים על אותו מחשב, פתחו כמה טאבים/חלונות של הדפדפן לאותה כתובת — כל טאב הוא "מכשיר" נפרד (זהות המשתתף נשמרת per-tab).

## שלב 4: פריסה לאחסון סטטי (Production)

כל הקבצים הם HTML/JS/JSON סטטיים — מתאים לכל שירות אחסון סטטי:

- **Vercel**: `vercel` מתוך תיקיית הפרויקט (או גרירת התיקייה בממשק הווב).
- **Netlify**: גרירת התיקייה ל-Netlify Drop, או `netlify deploy`.
- **GitHub Pages**: דחיפת התיקייה לריפו והפעלת Pages על הענף הרלוונטי.

אין צורך ב-build step — פשוט להעלות את כל הקבצים כמות שהם (כולל `content-packs/` ו-`assets/`).

## הוספת חבילת תוכן חדשה (בלי לגעת בקוד)

1. פתחו את `content-editor.html` (דרך השרת המקומי או האתר הפרוס).
2. ערכו את השאלות, ואת שדות **מזהה/שם/תיאור** של החבילה בראש העמוד. שינוי ה-**מזהה (id)** לפני ייצוא שומר את זה כחבילה חדשה ונפרדת — לא דורס את המקור.
3. לחצו **"ייצוא חבילת תוכן (JSON)"** — יורד קובץ `{id}.json`.
4. מקמו את הקובץ שהורד בתוך `content-packs/`.
5. הוסיפו שורה עבורו ב-`content-packs/manifest.json` (או לחצו **"הורדת הצעה מעודכנת ל-manifest.json"** בעורך, שמייצר `manifest.suggested.json` עם השורה כבר מוספת — בדקו אותו ושנו את שמו ל-`manifest.json`).
6. רעננו את מסך "יצירת חדר" — החבילה החדשה תופיע מיד ברשימת הבחירה.

## מבנה שאלה בחבילת תוכן

```json
{
  "topic": "core",
  "label": "תהליכי עבודה",
  "diff": "קלה",
  "q": "טקסט השאלה...",
  "opts": ["תשובה 1", "תשובה 2", "תשובה 3", "תשובה 4"],
  "correct": 0
}
```

- `topic` — מזהה קצר באנגלית (אפשר להמציא נושאים חדשים בכל חבילה).
- `label` — השם שמוצג בעברית במשחק.
- `diff` — `"קלה"` / `"בינונית"` / `"קשה"` (בדיוק כך) — קובע את סכום הזכייה בשלב בניית הקופה.
- `correct` — אינדקס התשובה הנכונה במערך `opts` (0 = הראשונה).

## איך עובד הסנכרון הרב-משתתפים (למי שממשיך לפתח)

- כל חדר משחק מיוצג כאובייקט אחד תחת `rooms/{roomCode}` ב-Realtime Database.
- כל מכשיר מאזין ל-`onValue` על `rooms/{roomCode}` ומעדכן את המסך שלו בכל שינוי.
- **רק המכשיר של השחקן הפעיל** (`activeDriverId` בחדר) כותב עדכוני משחק (`update()` עם עדכונים חלקיים — פתרון, קידום עמדה, שינוי קופה). שאר המכשירים הם צופים חיים בלבד, ולא כותבים — כך נמנעות כתיבות מתחרות בין כמה מכשירים בו-זמנית.
- שאלה נוכחית מסונכרנת דרך `currentQuestion.id` בלבד (לא הטקסט המלא) — כל מכשיר כבר טען את אותה חבילת תוכן (`packId`) בעצמו, ומחפש את השאלה לפי המזהה. כך נחסך תעבורה מיותרת ב-Firebase.
- הסבב הסופי (שלב 3) מתנהל על ידי אותו מכשיר שהיה פעיל אחרון (השחקן האחרון בתור) — אין "מנחה" נפרד; זה ממשיך את אותה לוגיקת "כותב יחיד" בלי צורך במושג תפקיד נוסף.
- טיימרים (30 שניות בבניית קופה, 45 בסבב הסופי) רצים מקומית אצל המכשיר הפעיל בלבד ואינם מסונכרנים בין מכשירים — שאר המשתתפים רואים רק את השאלה הנוכחית ואת התוצאה (נכון/שגוי), לא את הספירה לאחור. זו החלטת עיצוב מכוונת ל-MVP, לא מגבלה טכנית.

## ⚠️ הערה חשובה על תוכן

השאלות שמגיעות עם `content-packs/core-v1.json` (במיוחד אלו על "טופס 17") הן **שאלות דמו** שנוצרו להמחשת הקונספט בלבד, ואינן מאומתות מול נהלים רשמיים. לפני שימוש אמיתי בארגון:

- יש להעביר את כל בנק השאלות לאישור בעל ידע רשמי (למשל אמנון אשר או מומחה תוכן מוסמך).
- מומלץ להוסיף חבילות תוכן על תהליכים ומערכות אמיתיים של הארגון באמצעות `content-editor.html`.

## המשך פיתוח

הארכיטקטורה מפרידה בין מנוע המשחק (`index.html`), תוכן (`content-packs/*.json`), עורך התוכן (`content-editor.html`) והגדרות Firebase (`firebase-config.js`, `database.rules.json`) — כל שכבה ניתנת להרחבה בנפרד. רעיונות המשך אפשריים: ניקוי אוטומטי של חדרים ישנים (6+ שעות ללא פעילות), Firebase Auth אנונימי לחשיפה מחוץ לרשת הארגון, לוח מובילים חוצה-חדרים, וייצוא תוצאות לדוח.
